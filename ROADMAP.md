# GameDepot Roadmap

GameDepot is an open-source, community-driven game distribution and preservation platform (hard-forked from Drop OSS). This roadmap combines multi-store ingestion, chunked depot delivery, and native client capabilities. Store access and downstream redistribution must respect each provider's terms and users' legal rights.

---

## 🗺️ Phases & Milestones

### Phase 1: Stabilization & Clean Independence
*Decouple from upstream Drop OSS dependencies, clean up CI/CD, and streamline local developer onboarding.*
- [x] **CI Silencing & Streamlining:** Removed automatic `push`/`pull_request` CI triggers, converted pipelines to manual `workflow_dispatch`, and deleted unused static pages deployments.
- [x] **Monorepo Cleanup:** Audit workspace dependencies (`pnpm`, Rust toolchains), rebrand packages (`@gamedepot/server`, `@gamedepot/desktop`, `gamedepot-desktop` crate), and ensure clean independent builds for `server`, `desktop`, `torrential`, and `droplet`.
- [x] **Turnkey Docker Stack:** Provide an all-in-one `docker-compose.yml` and `.env.example` bundling the GameDepot server, PostgreSQL with healthchecks, persistent data volumes, and reverse proxy for self-hosting.

### Phase 2: Multi-Store Ingestion & Depot Repackaging
*Automate library discovery and reproducible acquisition from supported storefronts through isolated, headless adapters.*
- [x] **GOG Galaxy Ingestion:** Headless account authorization, library/build discovery, direct depot file streaming via Galaxy CDN / Content-System into 4 MiB Content-Addressable Storage (CAS), and immutable DropletManifest emission.
- [x] **Epic Games Ingestion:** Headless authentication (OAuth / Legendary exchange codes), entitlement discovery, asset manifest resolution, direct chunk/file streaming into 4 MiB CAS, and worker ingestion tasks with full test suites.
- [x] **Ubisoft Connect Ingestion (Optima adapter):** Evaluate `Starkka15/Optima` as a headless Ubisoft Connect acquisition adapter. Isolate account/session state; normalize owned products, editions and install/build metadata; stage only content the account is authorized to access. Treat it as an external, version-pinned adapter, not as GameDepot's catalog or trust boundary.
- [x] **EA App Sign-in and Entitlement Discovery:** Nucleus OIDC authentication via `accounts.ea.com` plus Help-session sign-in, entitlements/discovery via `ecommerce2.dm.origin.com` and Juno GraphQL at `service-aggregation-layer.juno.ea.com`, and the admin connection/discovery flows. Server-side DIP acquisition (remote ZIP parsing, range-based entry streaming) was removed as superseded by the launcher-based content model below: the live-service ZIP archive premise was never verified, and players' own launcher installs are the file source.
- [ ] **Launcher-Based Content and External Play:** Players keep titles current with their store launchers and contribute what they already own. The desktop client detects launcher installs (EA App install records on Windows and inside a umu storefront prefix), hashes them into the fixed 4 MiB CAS, uploads only the objects the depot lacks, and publishes through the shared adapter contract (admin-gated, provenance recorded); a manual Resync ships the diff after a launcher patch; file-owner copies can be played through the launcher itself (storefront prefix on Linux, native on Windows) instead of a second depot copy. `ArmchairDevelopers/Maxima` (`maxima-lib/src/content/downloader.rs`, `manager.rs`, `dip.rs`, `endpoints.rs`) is reference-only for EA launcher behavior, with no code copied.
  - Done: the server upload half — import sessions declare a release (paths, sizes, modes, per-chunk digests), the depot answers with the objects it lacks, arriving bytes are digest-verified into CAS, and commit publishes the `gamedepot-droplet` manifest, provenance and the pinned GameVersion through `utils/import/session.ts` + `utils/import/db.ts` under `api/v1/client/depot/import/session` (desktop-auth client routes, gated on the account's admin flag, 8 hermetic tests incl. digest parity with `publishDirectoryToCas`; chunked-release disk sizes now read from the CAS manifest, and the torrential version route refuses folder-less chunk-store versions).
  - Done: the desktop half too — `desktop/src-tauri/importer/` scans a folder in parallel, hashes it into the store's own fixed 4 MiB objects (client digests pinned to the SHA-256 vectors and to chunk-boundary splitting), opens a session, uploads only the missing objects at bounded concurrency with retry, and commits; `start_game_import` / `cancel_game_import` (`src/imports.rs`) drive it and report on the `import_state` event.
  - Done: and the import UI — Settings → Game files (admin-only nav entry) picks a folder, names the title, and optionally publishes under an existing catalog game; job rows show hashing/uploading/publishing with a byte progress bar and Cancel, driven by the `import_state` event through `main/composables/imports.ts`.
  - Done: the first recipe too — `importer/src/recipes/ea.rs` finds EA app installs from what the launcher itself wrote (the in-place install dir in `ProgramData/EA Desktop/machine.ini` and the per-account `user.downloadinplacedir` override, plus the conventional `Program Files/EA Games` roots), resolving each drive letter through the prefix's own `dosdevices` links so a games-on-a-second-disk library is found the way Wine sees it, and a folder on Windows is read the same way. A folder counts as an install only if it holds an executable that is not a redistributable, so uninstall leftovers do not offer themselves; a settings path that climbs out of its drive is refused instead of followed. Settings lists what it found, accepts a prefix the player points at, and prefills the form from a choice — nothing publishes without a press.
  - Done: whole-library import too — `importMany` in `main/composables/imports.ts` takes a detected set and runs it one folder at a time (sequential by design: two hundred-gigabyte scans would compete for the same disks), awaiting each job's terminal event through the same `import_state` stream, so a failure is one row in the summary rather than an abandoned library; Settings has an Import all button over the detected list.
  - Done: a detected install publishes under the game it belongs to — the detected list folds catalog and folder titles to a common shape (lower case, non-alphanumerics collapsed), a match offers Resync (one press, publishes a new version under that game id) and the whole-library batch passes the same match, so an import feeds the library into the catalog instead of beside it.
  - Done: launcher play too — a detected install carries the entry point the recipe found (`find_game_executable`: shallowest non-redistributable `.exe`, installer-shaped names skipped) and the prefix it lives in, and `play_launcher_install` runs that copy in place: natively on Windows, through umu-run + Proton on Linux, in the game's own prefix when it has one and a Drop `pfx/launcher/<slug>` otherwise. `src/launcher_play.rs` owns this path because the process manager is keyed to the install ledger a launcher-owned game has no row in; it waits on the child, reports playtime to the matched catalog game through the same rule depot launches use, and Stop kills the whole process group so no wine server survives the game. Settings shows Play/Stop on every detected row.
  - Done: the other storefronts too — `recipes/` now carries Epic, GOG, Rockstar, Steam and Ubisoft beside EA, all on shared machinery (the prefix-drive view, the path resolver, the executable rule, one cross-recipe `seen` set). GOG and Rockstar read conventional roots; Steam parses its library folders out of `libraryfolders.vdf` and searches each `steamapps/common`; Ubisoft Connect reads `game_installation_path` from the settings YAML in each account's AppData (verified against a real prefix's file); Epic reads its per-game `.item` manifests, so the folder, the app id (`install_key`, the first real identity hook) and the launcher's own recorded executable all need no guessing. Detection stays file-only — no registry, no live services — so a signed-out storefront still reports its games.
  - Done: the provider split the model implies — GOG and Ubisoft releases are the node's to keep current, EA and Rockstar the launcher's. The node asks its own connections: `api/admin/depot/{gog,ubisoft}/check-updates` compares each acquired game (`gog-<id>` / `ubi-<id>` rows, whose imported version names are the providers' own build identities - GOG's `versionName`, Ubisoft's deploy manifest SHA-1) against what the account is entitled to now, and queues the unchanged-from-ingest acquisition task for every newer build; owned-but-never-acquired titles are reported, never fetched. The admin depot page carries the button and the summary, `utils/depot/update-check.ts` holds the diff (pure, tested) and `utils/depot/ingest-queue.ts` the shared queueing. The desktop says the same thing in its own words: a GOG/Epic/Ubisoft row offers Upload (it seeds a copy the depot will update itself), an EA/Rockstar/Steam row offers Resync (its launcher copy is the update path), and every row plays with no storefront involved - the depot copy needs none, and Play runs the detected exe directly.
  - Done: launch mode becomes a property of the bytes — `GameVersion.runsStandalone` (migration `20261109000000_add_runs_standalone`, default true) is recorded when a release is published or imported, travels with the version document through sync, and the process manager refuses to direct-exec a false build with `ProcessError::StoreClientRequired` instead of letting it DRM-crash two seconds in. The import contract carries the declaration from the desktop's open-session call to the version row, and the import form is where it is made: a "This build starts without its store client" checkbox, defaulted per launcher (GOG and Epic true; EA, Rockstar and Ubisoft and Steam false), with a self-starting copy of a launcher-gated title corrected right there. Detected-copy Play is untouched — the player's own files run direct whatever the flag says — and the storefront handoff runner that plays false builds around their client is the next step. The same pass made the desktop's `version_path` optional, which chunk-store versions have always needed.
  - Done: Epic depot copies arrive with an install record — `games/src/epic_seed.rs` (unix-only) seeds the Heroic/Lutris shape into the game's own umu prefix at install completion: the `ProgramData/Epic/EpicGamesLauncher/Data` layout, a `<appid>.item` naming the app id and its conventional `Program Files/Epic Games` location, and a symlink from that Windows path to the real install directory, so an Epic bootstrapper reading its own prefix finds the depot copy instead of dying in the lookup. Best-effort by design — an install is complete without its record — and keyed to `epic-<appid>` catalog ids, so it is in place the day Epic acquisition (M6b) starts producing them.
  - Done: the check runs on the node's own calendar too — `depot:check-updates`, a daily scheduled task, scans the GOG and Ubisoft connections through `utils/depot/update-scan.ts`, the same shared scan the admin button answers from (the routes are now gates over it), queues newer builds of acquired games, and logs what it found; no stored connection is a skip, not a failure.
  - Done: Steam rows Play through the client — detection reads each library's `appmanifest_<appid>.acf` files so a detected Steam install carries its app id, and Play hands that id to the machine's own Steam client (`steam://run/<appid>`) when the client's own manifest says it owns the game — a file-only presence check, and the only player Steamworks content truly wants. Stop is the client's own `steam://stop`; the session's playtime files under the matched game by the same two-second rule. An app the native client does not own (a Steam living inside a umu prefix) still direct-execs as before.
  - Missing: the stronger EA-side identity match (offerId/content id against the entitlement list, replacing the title heuristic), a background watcher for auto-resync, Epic's acquisition decoder (its manifest bin format still needs a real sample before the 503 lifts), and handoff runners for the remaining storefront clients (EA protocol, Rockstar `GTAVLauncher PlayGame`).
- [x] **Installer / Disc Set Support:** Group split archives and multi-disc installers into ordered logical releases; verify expected parts and preserve source provenance.
- [x] **Common Adapter Contract:** `authorize -> discover -> normalize -> acquire -> verify -> publish`; make resync idempotent, redact secrets, and keep provider-specific formats out of shared catalog APIs.
  - The three provider streamers (GOG, Epic, Ubisoft) are ported onto it: each module keeps only provider knowledge and hands files to `stageAdapterRelease()` (`server/server/utils/adapter/contract.ts`), which owns path validation, chunk re-framing, size/digest verification and atomic publication.
- [x] **Store Connection Flows:** Heroic-style one-time sign-in for GOG and Epic persists an account connection (`api/admin/depot/connection/{gog,epic}` authorize/callback; EA offers the `login-url` initiator), lifecycle routes are gated with system ACLs, and GOG acquisition runs as a real persisted task.

### Phase 3: Player Features
*Native client functionality and integrations across devices.*
- [ ] **Cross-Device Cloud Saves:** Versioned backup, bidirectional synchronization, conflict resolution and rollback (incorporating Ludusavi manifest specifications).
  1. Server foundation (implemented): immutable `SaveVersion` history behind a movable slot head, content-identity hashes separate from archive checksums, `If-Match` optimistic concurrency with `409` conflicts, `Idempotency-Key` upload replays, restore-as-a-new-version, pinning, retention pruning with reference-counted object GC, a `sync` decision endpoint (`noop | push | pull | converged | conflict`, never decided by clocks), and per-game Ludusavi manifest reads. Legacy `historyObjectIds` arrays are backfilled and kept read-only for one release.
  2. Server verification (implemented): the save service is driven end to end against a real PostgreSQL 16 and the real filesystem object store (`pnpm e2e:saves`): head swap, stale-`If-Match` conflict leaving no row or object behind, `Idempotency-Key` replay, archive dedupe, every sync decision, gapless timeline paging, restore, pinning, retention pruning with reference-counted object GC, download byte-identity, the legacy `push` path, slot rules and size limits — 16 checks. A second driver (`pnpm e2e:saves-http`) exercises the HTTP contract against a live server — client-JWT auth, the capability gate, `If-Match` / `Idempotency-Key` / `X-Content-Hash` headers, the `409` body carrying `headVersionId`, download identity headers and ETag, restore/pin/delete, manifest reads and cross-user isolation — 16 more. Both are standalone scripts guarded to scratch-named databases (the suite itself has no database fixture); the migration's backfill is verified on PostgreSQL 16 and the pure modules are unit-tested.
  3. Desktop engine (implemented): `desktop/src-tauri/cloud_saves` is the engine now — it parses curated manifests (both Ludusavi entry shapes, `os:` conditions enforced, unknown condition keys fail closed), resolves placeholders per platform with Windows paths resolving inside the game's Proton prefix (`<data root>/pfx/<game_id>`), and keys each file by the template tail after its last placeholder, so a save is the same logical archive on Windows, Linux and Deck. Archives are deterministic `tar.zstd` (sorted keys, zeroed mtime/uid/gid, exec bit as the only portable mode) and the content hash byte-matches the server's — proven by cross-language vectors generated from the server's own `json-canonicalize` code. The client speaks the contract the e2e suite proved: `If-Match`, `Idempotency-Key` (replayed after unanswered uploads), the identity headers, `409`-as-conflict. Wiring: `launch_game` runs the pre-launch pull before the process lock (a save problem never blocks playing), process exit spawns the backup, every flow emits a `saves_state` event, and `sync_game_saves` drives the manual case; journal state (`SaveJournal` in `database`) makes retries cheap and safe. 21 unit tests cover hash vectors, archive determinism, Proton resolution, tamper refusal. Still open: a live desktop↔server round trip end to end, and the conflict/timeline UI below — v1 always asks, so nothing auto-resolves meanwhile.
  4. Client UX (implemented): the game page carries a Saves card — the version timeline (current/pinned/restore badges, file count and size per version), per-version pin and restore (restore never rewrites history: the server publishes a new head from the chosen version and the desktop applies it), and a "Sync now" action. A conflict opens an always-ask dialog — keep both (pin the server head, push the local save on top), keep local, or keep server — and a global hook routes the user to the right game when they notice it elsewhere. The engine never picks a side; versions are immutable, so every answer stays restorable from the timeline. Rust: `fetch_save_timeline` / `restore_save_version` / `set_save_version_pinned` / `resolve_save_conflict` over the engine's restore/conflict flows; frontend: `desktop/main/components/GameSaves.vue`, `composables/saves.ts`, global prompt in `composables/state-navigation.ts`. Verified: `nuxt typecheck` reports nothing in the new files (pre-existing errors elsewhere untouched) and `nuxt generate` builds clean; the two-device live conflict round trip still stands as the acceptance run for this feature.
  5. Storage quota and admin view (implemented): `saveUserStorageLimit` (MB, `0` = unlimited) caps what one account's whole save history holds across every game, profile and version, metered on the stored versions' `sizeBytes` — history that retention is about to prune is not free space an upload may spend. `createVersion` checks it twice: on the declared size before a byte is written, and again on the measured bytes after the stream, deleting the object when the real size does not fit; a refusal is a `400` naming what is stored, the limit and what the upload needs. `restoreVersion` is deliberately not gated — refusing to give a player their own save back is not what a quota is for. The client learns the cap from `GET /api/v1/client/saves/settings` (`userStorageLimit`, `features.storageQuota`). Admin: `GET /api/v1/admin/saves` lists every slot with owner, player, game, version count, head size and total footprint plus the per-user totals, `?user=`/`?game=` narrow it, and the slot (`…/slot/<userid>/<profileid>/<gameid>/<index>`) and version (`…/version/<versionid>`) routes read, download and delete through the same owner-scoped service methods the client uses — so a head stays undeletable (`400`) and a foreign key is a `404`, and there is no bulk purge to fat-finger. All of it is gated by `settings:update`, the ACL the save-manifest admin routes already use. `pages/admin/saves.vue` renders it in the existing admin shell (quota and per-slot progress bars, expandable timeline, download and delete behind a confirmation). Migration `20261106000000_save_user_storage_limit` (resumable), applied to the dev and e2e databases. Verified: manager e2e 17/17 (new check proves a quota refusal keeps head, version count, usage and the object directory untouched, and that the same bytes land once the limit is raised), HTTP e2e 29/29 against a live server (advertised quota, admin list, byte-identical admin download, over-quota `400` then the same push fitting after the cap lifts, version and slot deletes, a client JWT refused on an admin route); typecheck, `eslint server/ components/` and 243 unit tests clean; deployed as `20261103-052601` with route-level curl checks (list `200`, bad index `400`, unknown version `404`). The admin page is typecheck- and build-verified but not yet clicked through in a browser with real rows.
- [ ] **Multi-Profile Support:** Isolated configs, play stats, accounts, and save states per profile.
  1. Server foundation (implemented): a `Profile` row is one player inside an account (name, `isDefault`). Every account always has a default named "Player" — the migration backfills one per existing user and `profileManager` lazily recreates it for anything older, so no code path ever reasons about "no profile". Playtime, save slots and save versions all carry `profileId` inside their compound keys; the migration widens those keys in place and attributes every existing row to its owner's default profile, so the upgrade preserves data exactly. Client requests name their profile with `?profile=<id>` or the `x-profile-id` header and fall back to the default; a foreign id is a 404 and a malformed one a 400 — never a silent default. Profiles are CRUD-light on purpose: `GET/POST /api/v1/client/profiles` plus rename via PATCH, no delete, because a profile owns play stats and a save timeline that outlive a rename. Library membership stays account-wide; per-profile store connections wait for v2 (`StoreConnection` has no user today, let alone a profile), and config isolation is a desktop-side concern.
  2. Contract proof (implemented): both e2e suites now run profile-scoped — the manager suite attributes everything through the default profile (which also proves its lazy creation), and the HTTP suite pins the wire contract against a live server: selectorless requests land on the default profile, add/rename works, one profile's saves and playtime are invisible to another (slot lists, timelines, version ids and totals all stay apart), and unknown or malformed selectors are refused rather than silently defaulted. 16/16 manager checks (scratch database) and 21/21 HTTP checks (a running instance, as the harness requires) green.
  3. Desktop attribution (implemented): the active player lives in the local database (`currentProfileId`; `None` means "the account's default", matching pre-profile behaviour exactly, so old databases stay valid) and every request the app makes — playtime reports, the library fetch whose rows embed play stats, all save sync/upload/restore traffic — carries it as `x-profile-id`. Journal keys are per-player, so "what did this device last sync" is tracked per player, with the pre-profile key left untouched for accounts that never open the switcher. Switching players clears the cached library so stats from the previous player cannot linger. Commands: `fetch_profiles` / `create_profile` / `rename_profile` / `set_current_profile` / `get_current_profile`.
  4. Switcher UI (implemented): the account menu carries a "Play as" list — every player with a check on the active one — and a "Manage players" link into a settings page that adds players (prompt), renames them (stats ride through), and hands out the active role. Switching refetches the library, so play stats on screen are the new player's immediately; the menu section appears once a second player exists, so single-player installs see no change. Frontend: `composables/profiles.ts` (shared `useState` roster the header and settings agree on), `pages/settings/profiles.vue`, the section in `HeaderUserWidget.vue`, sidebar entry in `pages/settings.vue`. `nuxt typecheck` clean on the new files and `nuxt generate` builds. Not yet run: the two-player live flow on a real install (create → play → switch → saves and stats stay apart) — same acceptance run the cloud-saves work still owes.

### Phase 4: Next-Gen Storage & Chunked Delivery
*Deduplicated, verifiable delivery using manifest-driven depots and seekable compression.*
- [x] **Manifest / Chunk Depot Model:** Study DepotDownloader's Steam-style depot workflow: app/depot/build manifests enumerate paths, file metadata, chunk identities, offsets/sizes, and integrity data. Define a provider-neutral immutable manifest schema and explicit mapping from logical files to content objects; do not bind GameDepot to Steam's private protocol or require Steam credentials.
  - Shipped as `gamedepot-droplet` v1: fixed 4 MiB content-addressed chunks, per-file `path`/`size`/`sha256` with ordered chunk identities, a `chunkIndex` mapping each chunk digest to its content object, and a canonical-JSON digest making every manifest self-digesting. Provider adapters emit it; nothing in the schema is store-specific.
  - Unified from the server side: `gamedepot-droplet` v1 is now the externally-consumable format too. `POST /api/v1/admin/game/:id/versions/:versionid/chunk` chunks a library release into a content-addressed depot under `<DATA>/depot` (deduped across versions, manifest written last, per-file `mode` so an assembled Linux install keeps its executable bits); `GameVersion.casManifestDigest` pins the release, and `GET /api/v1/client/depot/manifest` plus `GET /api/v1/client/depot/content/:versionid/:sha256` serve it to any authenticated client with immutable ETags. Verified live against a 2.1 GB / 759-file release: the served manifest bytes recompute to the digest the row names, and fetched chunks hash to the digests they were requested by (`server/e2e/depot-cas.e2e.ts`, 13 checks). Upstream's 64 MiB manifest is untouched and still serves Drop CDN depots. Unified from the client side too: the desktop agent now probes each version's v1 manifest when a download starts and takes the chunk-store path when one exists (`desktop/src-tauri/games/src/downloads/cas.rs`) — fetch by digest, SHA-256 verified *before* a chunk enters the shared cache, files assembled in staging and renamed into place only after the whole-file digest checks, manifest `mode` applied (mode 0 falls back to 0644), a delta's two versions splitting cleanly between the two sources while `fileList` ownership still gates every write. Versions with no v1 manifest — every Drop CDN depot among them — keep taking the upstream path untouched. Hermetic tests in `cas.rs` pin the publish-only-if-verified order; a live desktop install of a chunked release is the remaining acceptance run.
- [ ] **Chunk Acquisition & Assembly:** Support concurrent, bounded and resumable retrieval of manifest-addressed chunks; validate lengths and hashes before caching; assemble files in staging and atomically publish only after final verification.
  - The v1 path (`games/src/downloads/cas.rs`) now does exactly this for chunked releases: bounded parallel fetches, length+digest validated before the chunk is cached, staging plus a rename-per-file publish after the whole-file hash, and a digest-keyed cache that survives restarts. What is missing still: the same order for the upstream V2 path (whose checksum arrives only after its stream was already written in one pass — one more reason new content should grow on v1), and an install-pointer switch that keeps the previous version active until the target passes validation.
- [ ] **Seekable Zstandard (zstd):** Repackage verified source files into independently decodable frames with an index mapping logical file ranges to compressed byte ranges. Version manifests and frame layout; verify compressed and decoded content and expose HTTP range reads where supported.
- [ ] **Steam-Style Delta Patching:** Compare old/new file and chunk identities, reuse unchanged verified objects, acquire only missing/changed chunks, and preserve the old usable install until the new release passes validation.
- [ ] **Transfer Engine Evolution (`droplet` / `torrential`):** Bounded parallel fetching, cancellation, retry, progress reporting, integrity verification, cache lifecycle, and on-demand decompression.

### Phase 6: Native Client Polish & Linux / Steam Deck
*Unified desktop and handheld launch experience.*
- [x] **Rich Metadata & Scrapers:** Cover art, banners, logos and screenshots.

## 💡 Future idea: Cache Node (read-through depot cache for LAN/offline use)
A small node that sits between clients and the main GameDepot server so LAN parties and offline setups pull bytes locally instead of over the WAN.

### Milestone 1 — Proxy node (plumbing, low risk)
- Small Docker image (the repo-root `Dockerfile`/`docker-compose.yml` can be extended or run in parallel) that fronts the main GameDepot server.
- Manifest + metadata requests: always forwarded live to upstream (tiny, keeps versions in sync automatically).
- Content/blob requests: forwarded upstream (no caching yet); auth tokens validated against upstream so the node can't act as an open proxy.
- Client gets a "cache URL" config that overrides the server URL.

### Milestone 2 — Blob cache
- Content-addressed cache on the node's volume — since the depot layer is content-addressed, a cached blob can never be stale; eviction = drop a file, no invalidation logic.
- LRU eviction with a disk quota.
- Serve-on-miss (proxy) vs. cache-only mode (only serve what's pre-cached).

### Milestone 3 — Admin control of what's cached
- Server-side admin UI action: "pre-cache game/version → node X" so the cache can be filled over the home connection before the LAN party.
- Pin games (never evict); everything else LRU.
- Node status view: disk usage, what's resident, cache hit stats.

**Suggested placement:** before/alongside user libraries — the Epic appName correctness fix already landed (appName is required by the ingest route, sent in the launcher-assets query and used in the manifest download URL `/appName/<name>/manifest/`), so it no longer gates this work. The cache key design (game vs. per-chunk) should still be decided early because it affects the ingest manifest format.

**Design decision to settle first:** per-chunk caching vs. whole-file caching. Per-chunk is what makes pre-caching and bandwidth-sharing cheap, but it couples to the depot download protocol more tightly. Current lean: per-chunk, since the protocol already streams in chunks.
